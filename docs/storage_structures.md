## 2. Task 3.2: Storage Structures in Azure SQL Database

In Azure SQL Database (Microsoft Transact-SQL engine), table storage architectures differ from theoretical textbook file organizations due to cloud storage abstractions, 8KB data page structures, and B-tree allocation:

### 1. Clustered Index (B-Tree Data Storage)
- In Azure SQL Database, a table can have at most one **Clustered Index**. When a clustered index is created, the actual data rows of the table are stored in the leaf nodes of the B-tree ordered by the cluster key.
- By default, Azure SQL assigns the clustered index to the `PRIMARY KEY` constraint.
- **Mapping**: For tables where access is dominated by point lookups or range scans on the primary key (`Customer`, `Assembly`, `Department`, `Process`, `Job`, `Cut_Job`, `Paint_Job`, `Fit_Job`, `Account`, `Assembly_Account`, `Department_Account`, `Process_Account`), we retain the default **Clustered Index on the Primary Key**.

### 2. Nonclustered Indexes (Secondary B-Trees)
- Azure SQL supports standalone secondary B-tree indexes where leaf pages store the index search key plus a row locator (the clustered key or RID for heaps).
- **Secondary Index on Job**: `CREATE NONCLUSTERED INDEX idx_job_asm_commence ON Job (assembly_id, commence_date);`
  - *Justification*: Query 11 ($100$/day) retrieves processes passed through by an assembly in `commence_date` order. This composite nonclustered index covers the query without table spooling or costly sorting.
- **Secondary Index on Customer**: `CREATE NONCLUSTERED INDEX idx_customer_category ON Customer (category) INCLUDE (address);`
  - *Justification*: Query 12 ($100$/day) and Option 16 perform range filtering on `category`. Leaf-level index seeking avoids scanning all customer rows.
- **Secondary Index on Process**: `CREATE NONCLUSTERED INDEX idx_process_dept ON Process (dept_no);`
  - *Justification*: Accelerates Query 10 department-level joins and enforces referential checking.

### 3. Heap File Architecture
- A table without a clustered index is stored as a **Heap**. Tuples are written to any page with free space without sorting.
- In Azure SQL, heaps are suitable for staging tables or pure append-only logging tables. However, Microsoft best practices strongly recommend a clustered index for all production tables with primary keys to prevent page fragmentation, forward pointer chains, and heap allocation bloat.
- Therefore, for `Cost_Transaction`, while theoretically modeled as a heap in Task 3.1, in Azure SQL Database we implement a **Clustered Index on `trans_no`** with a nonclustered index on `job_no` to maintain optimal transactional integrity and query execution speed.
